Come with an idea, leave with an office.

Studio is an opt-in mode, per project: a plan, a roster and a six-column board that live in your repository, and — eventually — one real coding session per role, found by the same scan as everything else.

Four of the eleven steps exist, and the tag on each step below says which. Enabling a project writes one file and records the grant. Hire writes no worktree, starts no role session and adds no board tab.

Eleven steps, and the whole design is that ten of them reuse something the floor already does. The full version is docs/07-STUDIO-DESIGN.md.

What exists today.

Studio is off everywhere and does nothing until you enable it for a directory.

  • The store, and the consent

    enable --yes writes exactly one file — <project>/.deckhq/studio/README.md, carrying a marker on its first line — and records the path and the grant. Everything else in that directory, when it arrives, is yours. It is not gitignored, because a plan is something a team should be able to commit.

    deckhq studio enable ./my-project

    Without --yes it prints every path it would write and changes nothing.

  • Taking it back

    disable --yes deletes only files that still carry the marker and names everything it left alone. A path that would resolve outside .deckhq/studio/ — by .., by being absolute, or through a symlink — is refused with the offending path rather than quietly clamped back inside.

    deckhq studio disable ./my-project --yes

    Consent is per project and is never inferred from another.

Grill: the interview that writes the plan.

Once a project is enabled, ⌘K → Studio: plan this project starts a planner. It is a real claude session in that directory with an interview brief as its first prompt, so it walks onto the floor on the next scan, takes a desk, and you answer it in the ordinary panel composer.

It asks, in turn, for the goal, the non-goals, the constraints, the milestones with their acceptance criteria, and the roles you need. Then it writes blueprint.md, roster.json and board.json and says written.

DeckHQ writes none of them. The planner writes them, as ordinary files, with its own tools. DeckHQ reads them back and checks them, and one that does not check out is reported with its name, its line and the reason — and left exactly as it was written.

The brief itself is yours too: edit it and DeckHQ will never overwrite it; a regeneration is written beside it and yours is what runs. Claude Code only for now — another runtime is refused by name rather than handed a brief nobody has run it against.

The rule the board runs on

A card’s column is yours.

No session ending, no test passing, no file appearing and no budget being spent moves a card. They flag it; you move it. It is the same rule the queue runs on, and it is the reason both are worth having.
