Adapters

Every runtime DeckHQ reads sits behind one interface. Nothing outside src/adapters/ reads a transcript or shells out to a runtime CLI, which is what makes a third runtime an addition rather than a rewrite.

What ships today

Runtime Status What it gives you
Claude Code Verified, and the runtime the product is developed against Transcripts on disk, live sessions from claude agents --json, hooks for exact state, sending a turn, opening a session in a terminal, and the plugin route.
Codex Unverified Rollout files, sessions, and the same hook shape. Implemented, tested against fixtures, never run against real Codex data.

Treat DeckHQ as a Claude Code tool until the Codex adapter has been exercised end to end. It is written against documented rollout-file conventions, but Codex is not installed on the development machine, so no line of it has met real data. It reports itself unavailable cleanly and degrades without throwing rather than guessing. When it runs on a machine with Codex on it, this page says so instead.

The interface

An adapter answers six questions and owns a hook block. This is the whole contract, from docs/02-ARCHITECTURE.md §2: 

interface RuntimeAdapter {
  readonly id: string;
  readonly label: string;

  /** Is this runtime present on the machine? Cheap, cached for the process lifetime. */
  available(): Promise<boolean>;

  /** Sessions the runtime reports as currently alive. */
  liveSessions(): Promise<LiveSession[]>;

  /** Every session on disk, newest first, bounded by opts. */
  scanSessions(opts: { maxAgeDays: number; limit: number }): Promise<SessionSummary[]>;

  /** Full message list for one session, most recent last. */
  conversation(id: string, opts: { maxMessages: number }): Promise<Message[]>;

  /** Send a turn into a session. Resolves when the runtime returns. */
  send(id: string, text: string, opts: { cwd: string; timeoutMs: number }): Promise<SendResult>;

  /** Spawn an interactive terminal attached to this session. */
  openInTerminal(id: string, cwd: string): Promise<void>;

  /** Adapters without hooks return supported: false and the daemon degrades. */
  hooks: {
    supported: boolean;
    describe(port: number): HookPlan;   // exactly what would be written, for the consent screen
    install(port: number): Promise<void>;
    remove(): Promise<void>;
    installed(port?: number): Promise<boolean>;
    installedPort(): Promise<number | null>;
  };
}

Adding a runtime means adding one entry to the registry in src/adapters/index.mjs. Nothing else in that file changes, and nothing outside src/adapters/ changes at all.

The rules a new adapter has to keep

  • All parsing lives in one file per adapter. On-disk formats are undocumented and they break; a format break should be a single-file fix.
  • A parse failure on one session must never fail the scan. Log it, skip that session, carry on.
  • Prefer a supported CLI surface over file parsing wherever both exist — that is what liveSessions is for.
  • An unavailable runtime degrades, it does not throw. A machine without your runtime should not know your adapter is there.
  • No network egress, and no runtime dependency. Both are rejection criteria regardless of how good the rest of the change is.
  • The invariant holds. No observed event an adapter reports may clear a state the user owns.

Contributing one

An adapter is the most useful thing an outside contributor can add, because the person who runs the runtime is the only one who can verify it. The route:

  1. Read CONTRIBUTING.md first. It leads with the two things that get a change rejected regardless of quality: the invariant, and network egress of any kind.
  2. Copy the shape of src/adapters/codex/ — it is the smaller of the two and shows the minimum an adapter has to answer.
  3. Put your fixtures in test/fixtures/ and your parse tests beside the existing ones. The suite is node --test; there is no framework to learn.
  4. Say in the pull request whether you have run it against real data on your own machine. An adapter that has is marked verified here; one that has not is marked unverified, in the same words as Codex above.

A claim in anyone’s documentation is a hypothesis until it has been measured on a machine. That rule applies to this project’s own claims first, which is why the row above says unverified rather than supported.
