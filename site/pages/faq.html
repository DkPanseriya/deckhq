FAQ

Answered with what has been run on a machine. Where something has not been, the answer says so.

Why not just use claude agents?

Because they answer different questions. claude agents lists what is running. DeckHQ keeps what is owed.

When a session finishes its turn and its process exits, it leaves that list — correctly, because it is no longer running. What nothing then records is that it asked you a question twenty minutes ago and is still waiting for the answer. That record is the entire product: DeckHQ reads every transcript on disk, so a finished session is still on the floor with what it last said, and it stays there until you discharge it. Opening it does not. Reading it does not.

Here is the same machine, counted both ways, on 3 September 2026:

  transcripts     77 sessions across 20 projects
  running now     6   (claude code's own agent view reports 6)
  on the floor    77  ← 71 sessions have already finished; the agent view no longer lists them
  waiting on you  0   (3 waiting, all still running)

Note what the last row is doing. Three sessions want something, and DeckHQ counts none of them as work anything has forgotten — because all three are still running, so the runtime’s own view lists them too. It reports the number it can substantiate, which is the only kind worth reporting. Run npx deckhq doctor and you get your own; it is usually surprising, because nobody counts finished sessions.

The agent view is also moving: recent builds group sessions as Pinned, Ready for review, Needs input, Working and Completed. That grouping covers background sessions and sessions with pull requests rather than transcripts on disk, which is why the numbers above still differ — and the day they stop differing, this answer gets rewritten rather than repeated.

Does it send anything anywhere?

No. No analytics, no telemetry, no update check, no crash reporting, no CDN, no account. The daemon binds 127.0.0.1, there is no --host flag, and the only other sockets are the runtime processes DeckHQ starts on your behalf. deckhq doctor’s last line reports the egress it found, and Hooks and privacy lists every path it reads and writes. This site keeps the same promise: it loads no fonts, no scripts and no images from anywhere but its own origin.

Do I have to install the hooks?

No, and DeckHQ is useful without them. Hooks buy you two things: exact, instant state instead of state inferred from a transcript, and the ability to tell needs_input from stalled, which a transcript alone does not distinguish. Without them the header says so plainly rather than showing you a confidently wrong picture. Nothing is written to your settings file until you have seen the literal JSON and clicked, the file is backed up first, and removal deletes only the tagged entries DeckHQ wrote.

Does DeckHQ run my agents?

No. It is the layer above whatever you already use. You start your sessions wherever you normally start them — a terminal, an editor, a script — and they turn up on the floor because their transcripts are on the disk. There is no manager agent, nothing is spawned to make it work, and nothing on the floor costs a token to be there.

Which runtimes does it read?

Claude Code, verified. Codex, implemented and unverified — it has never run against real Codex data. Adapters has the detail and the interface for adding one.

Which platforms?

The product is tested in CI on Windows, macOS and Linux against Node 18, 20 and 22. Two features are honest exceptions: “open in terminal” has been run for real on Windows only — the macOS and Linux emulators are implemented against each one’s documented interface and unit-tested down to the exact argument list, and executed nowhere — and OS notifications are in the same position.

Do I have to keep the tab open?

No, and the point is that you should not have to. The daemon outlives the browser tab: state keeps accruing while you are not looking, because that is when debts accumulate. deckhq waiting answers from the terminal, deckhq statusline puts ▣ 3 waiting · 1 hand up in a status bar, --notify raises an OS notification for the two events worth interrupting you, and an installed DeckHQ badges the dock icon with the count while every window is closed.

Is the cost number my bill?

No. DeckHQ multiplies observed token counts by public list prices so you can compare projects against each other. It has no idea what your plan actually charges you, and it is labelled an estimate everywhere it appears. Totals for very large transcripts are approximate as well: reads are bounded to keep scans fast, so a multi-gigabyte session’s historical usage is sampled rather than summed.

Is it free? Will it stay free?

MIT, and the local product stays that way. There are paid services planned above it — the kind that need a server, like one floor across several machines — and the rule binding them is that they are things you opt into, never gates on the local interface. Capture, the queue and every action stay in the free core, and the free product keeps making no outbound connections at all.

Where is my data, and how do I get rid of it?

In ~/.deckhq/, on your own disk — the queue, bench states, names, settings, the cache and the ledger. Delete the directory and there is nothing left of DeckHQ on the machine. DECKHQ_STATE_DIR moves it somewhere else.

Why an office?

Because a manager walking onto a floor gets, for free, what a list of session ids never gives you: who is busy, who is stuck, who is waiting to talk to you, and who is free. The metaphor has exactly one job — make agent state legible at a glance — and every element on the floor maps to a real state. Nothing on it is decorative only.

The floor also has a failure mode this project takes seriously: something beautiful is something you leave open and watch. The job of this product is to let you stop watching, which is why the terminal deck, the status line, the notifications and the daily numbers all exist.

Something is wrong. Where do I say so?

Issues, with the output of deckhq doctor --share if it is about your machine — that block has your paths, project names and machine name taken out of it already. Security reports have their own route in SECURITY.md. What shipped and when is in the changelog; why it shipped that way is in the engineering log.
