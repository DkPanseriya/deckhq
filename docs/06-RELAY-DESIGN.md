## 0. Read this first

This is a protocol and a threat model, not a feature list. It exists so that the ten days of
WP-32 are spent building rather than deciding, and so that the two claims the relay is sold
on — *the relay cannot read anything* and *the free product still makes zero outbound
connections* — are decisions in a document before they are sentences on a pricing page.

Three rules govern how it is written.

1. **Every claim about a third-party API carries a URL and a retrieval date.** They are in §14.
   Four claims could not be verified from primary documentation and are labelled
   **`UNVERIFIED`** in place. Per `08` §1.1 rule 11 they are hypotheses, and the first day of
   WP-32 is a spike that turns each one into a measurement or a redesign.
2. **Nothing here goes in a README, a tweet or a pricing page** until it has run on a machine.
   This is the same standing rule that keeps WP-19 out of the README (§97), and the relay is a
   larger promise than WP-19 is.
3. **Where this document and a shipped behaviour disagree, the shipped behaviour wins and the
   difference gets a `DEVIATIONS.md` entry.** The blueprint's rule, not a new one.

### 0.1 The one-paragraph summary

The daemon holds a single outbound WebSocket to a relay, and only while the user is signed in.
Everything it sends is AES-256-GCM ciphertext under a 256-bit *floor key* that is minted on the
first machine and handed to each new device through an X25519 agreement performed at pairing,
authenticated by a QR code on the floor and a six-digit confirmation. The relay routes opaque
envelopes between the devices of one room and stores a bounded queue of them for devices that
are asleep. It can see device identifiers, timings, sizes and connection metadata. It cannot see
a session title, a line of conversation, a path, a project name, a hostname, a model name or a
token count. Actions travel phone → daemon and go through `act()` exactly like a click on the
floor; the phone never writes state, and nothing the relay or the phone observes can clear an
acknowledgement.

### 1.1 What the relay is actually selling

`08` §3.0.3 is the correction that shapes the whole product: **a phone window on one session is
free elsewhere.** Claude Code Remote Control is on all plans, Happy is MIT with a free hosted
relay, Paseo pairs a phone across five runtimes. If the pitch is "see your session on your phone",
the price is zero and we lose.

What is not free anywhere:

- **Every session on every machine.** Four machines, four runtimes, one floor — including
  sessions nobody started from the app, which is the capture moat (M2) extended across a network.
- **Every session, including the ones that ended.** The invariant is what makes a two-day-old
  `for_review` still visible; that property travelling to a phone is not a phone window, it is a
  queue.
- **History that survives a machine.** The ledger's day files (§100), merged by `machineId`.
- **Approve from anywhere** (§97), if and only if the live run happens.

Every design choice below is scored against that list. A choice that makes the phone prettier and
the multi-machine story weaker is the wrong choice.

### 1.2 What "the relay cannot read anything" has to mean

It has to mean the strong thing, because a weaker version is a lie that a competent reader will
find. Concretely:

- The relay operator, with full access to the database, the process memory and every byte on the
  wire, cannot recover any conversation text, session title, file path, project name, machine
  name, model name, token count or cost estimate.
- That property survives the operator being compelled, compromised, or dishonest.
- It does **not** hide that a room exists, how many devices it has, when they connect, how often
  they exchange envelopes, or roughly how large those envelopes are. §4.4 states exactly what is
  visible, and §10 states what can be inferred from it.

## 2. The shape

### 2.1 Terms

| Term | What it is |
|---|---|
| **Floor** | One user's set of paired devices. The unit of encryption and the unit of billing |
| **Device** | A daemon on one machine, or one browser profile running the PWA. Minted locally, never by the relay |
| **`roomId`** | 128 random bits, hex, minted with the floor. The relay's routing key. Stable for the life of the floor |
| **`deviceId`** | 128 random bits, hex, minted by the device at pairing |
| **`machineId`** | The 32-hex identifier the ledger already mints (§100 decision 6). One per machine, reused; the relay never sees it in clear |
| **Floor key `FK`** | 256 random bits, minted by the first daemon. Never leaves a device unwrapped |
| **Epoch** | A `uint32` counter on `FK`. Rotation mints a new `FK` and increments it |
| **Device identity keys** | Per device: one X25519 pair (agreement) and one Ed25519 pair (authentication). Private halves never leave the device |
| **Relay** | The routing service. `relay.deckhq.dev`, or any URL the user names |

### 2.2 The trust boundary

```
   machine A                     machine B                    phone
 ┌───────────────┐             ┌───────────────┐          ┌──────────────┐
 │ daemon        │             │ daemon        │          │ PWA          │
 │ FK, seqA      │             │ FK, seqB      │          │ FK, seqP     │
 │ act(), store  │             │ act(), store  │          │ render only  │
 └───────┬───────┘             └───────┬───────┘          └──────┬───────┘
         │ outbound WSS                │ outbound WSS            │ WSS
         └──────────────┬──────────────┴─────────────────────────┘
                        ▼
              ┌────────────────────┐          ┌──────────────────────┐
              │ relay (room R)     │─ push ──▶│ push service         │
              │ routes ciphertext  │          │ (FCM / APNs / Mozilla)│
              │ bounded queue      │          └──────────────────────┘
              │ device registry    │
              └────────────────────┘
       ─────────────────────────────────────────────  trust boundary
       above: plaintext exists      below: ciphertext and metadata only
```

Three properties of that picture are load-bearing.

1. **`act()` runs on exactly one side.** A daemon owns the sessions on its own machine and is the
   only writer of their ack state. The phone renders and sends requests.
2. **The relay is on the wrong side of the boundary and knows it.** It is designed as an
   untrusted router. A relay that starts behaving badly can drop, delay, reorder and count. It
   cannot forge, read or replay (§4.3).
3. **The push service is a second untrusted party**, and a different one — Google, Apple or
   Mozilla, chosen by the user's browser, not by us. §7 treats it as hostile to content.

### 2.3 Why one floor key rather than pairwise keys

The alternative is a key per (daemon, phone) pair, which is what a naive read of "derived at
pairing" produces. It was rejected:

- A phone paired in October must be able to read a day file the daemon wrote in September. With
  pairwise keys the daemon must re-encrypt 90 days of history per new device, on a machine that
  may be off.
- Four machines and two phones is eight keys, eight sequence spaces and eight revocation stories.
- Multi-machine is the product (§1.1). A design whose cost grows with machines is the wrong
  design for the thing being sold.

The cost of one floor key is stated plainly and carried in §10: **any device that holds `FK` can
read everything on the floor.** A lost phone is therefore a floor-wide event and its remedy is an
epoch rotation, not a device deletion. That is why §3.5 makes rotation automatic on revocation
rather than a thing the user has to know to do.

### 2.4 Primitives, and why these ones

C8 forbids a runtime dependency, so the primitives are the intersection of what `node:crypto`
ships and what WebCrypto ships. That intersection is not large and it decides the design.

| Purpose | Primitive | Daemon | Phone |
|---|---|---|---|
| Agreement | X25519 | `generateKeyPairSync('x25519')`, `crypto.diffieHellman()` | `SubtleCrypto` `X25519` deriveBits |
| Key derivation | HKDF-SHA-256 | `crypto.hkdfSync` | `SubtleCrypto` HKDF |
| AEAD | **AES-256-GCM**, 96-bit nonce | `createCipheriv('aes-256-gcm')` | `SubtleCrypto` AES-GCM |
| Device authentication | Ed25519 | `crypto.sign(null, …)` | `SubtleCrypto` Ed25519 |
| Randomness | CSPRNG | `crypto.randomBytes` | `crypto.getRandomValues` |

**AES-GCM rather than ChaCha20-Poly1305, and the consequence.** `node:crypto` offers
`chacha20-poly1305`; WebCrypto does not list it (MDN, §14 R7). XChaCha20's 192-bit nonce, which
would have allowed random nonces with no bookkeeping, exists in neither. So the AEAD is AES-256-GCM
with a 96-bit nonce, and a 96-bit nonce is far too short to pick at random for a long-lived key.

**Therefore the nonce is deterministic, and the sequence number is not only replay protection —
it is the nonce.** `nonce = epoch (4 bytes, big-endian) || seq (8 bytes, big-endian)`. A repeated
`(key, nonce)` pair under GCM is a catastrophic failure: it leaks the XOR of two plaintexts and,
worse, the authentication subkey. §4.3 spends a paragraph on the persistence discipline that makes
a repeat impossible across a crash, because that paragraph is the most safety-critical text in
this document.

`UNVERIFIED` — that `crypto.diffieHellman({ privateKey, publicKey })` accepts X25519 key objects
on the project's Node floor (`>=18`) was not confirmed against primary documentation during this
design (§14 R8 lists X25519 key *generation* and Ed25519 sign/verify as confirmed, and does not
settle the agreement call). Day 1 of WP-32 runs it on Node 18, 20 and 22 across the three CI
platforms. If it is absent on 18, the floor moves to the lowest Node that has it and
`package.json` `engines` moves with it, in the same commit, with a `DEVIATIONS.md` entry.

`UNVERIFIED` — WebCrypto `X25519` and `Ed25519` are listed by MDN as SubtleCrypto algorithms
(§14 R7) with an explicit caveat that per-algorithm support varies by browser. WP-33 day 1 runs a
feature probe on the four target browsers before any of WP-33's UI is written. If Safari lacks
`X25519`, the fallback is P-256 ECDH, which every browser has had since 2017, at the cost of a
worse curve and one more paragraph in the threat model.

## 3. Pairing

### 3.1 The user's experience, in full

1. On the floor: **Settings → Relay → Pair a device**. The daemon signs in first if it has not
   (§3.7), opens its WebSocket, and displays a QR code plus the same payload as text.
2. The phone opens `https://relay.deckhq.dev/p#…` — the fragment, so the payload never reaches
   the relay's logs, its access logs, or a proxy — and the PWA offers **Install**.
3. Both ends compute a six-digit number. The phone shows it large. The floor shows a dialog:
   *"A device says it is `iPhone (Safari)`. It shows **418 209**. Does yours?"* with **Match** and
   **Cancel**.
4. On **Match**, the daemon wraps `FK` to the phone and adds it to the device list. The phone
   draws the deck within a second.
5. The floor shows a permanent row in Settings → Relay: device name, when it paired, when it was
   last seen, and **Revoke**.

Step 3 is not decoration. See §3.4.

### 3.2 The QR payload

```
deckhq-pair:v1
  h  relay base URL            (https://relay.deckhq.dev, or the self-hosted one)
  r  roomId                    32 hex
  n  rendezvous                32 hex, single use, 120 s TTL
  dk daemon X25519 public key  base64url, 32 bytes
  ds daemon Ed25519 public key base64url, 32 bytes
  m  daemon display name       "tower", user-editable, defaults to the OS hostname
```

`m` is the only human-meaningful field, it is on the user's own screen, and it never leaves the
two devices — it is carried inside the pairing ciphertext, not in the QR's transport to the relay.
The QR itself is rendered locally from a vendored, dependency-free encoder in `public/`, because
a QR generated by a CDN would be an outbound connection and C1 does not have exceptions.

### 3.3 The ladder

Both devices hold long-term identity keys. The phone's are minted on first load of the pairing
page and stored non-extractable in IndexedDB (§7.5). The daemon's live in
`~/.deckhq/relay.json`, mode `0600` — with the same honest caveat the ledger's signing key
carries (§100): **on Windows that mode is not enforced**, and the file's protection is whatever
the user's profile directory provides.

```
ss    = X25519(daemon_id_priv, phone_id_pub)          // and the mirror on the phone
prk   = HKDF-Extract(SHA-256, salt = roomId ‖ rendezvous, ikm = ss)
wrap  = HKDF-Expand(prk, "deckhq/pair/v1 wrap", 32)
sas   = HKDF-Expand(prk, "deckhq/pair/v1 sas",  4)    // → uint32 mod 10^6, zero-padded
```

The floor key is then wrapped and sent through the relay:

```
wrapped = AES-256-GCM(key = wrap,
                      nonce = 0^96,                    // one use, one key, by construction
                      aad = "deckhq/pair/v1" ‖ roomId ‖ epoch ‖ daemon_deviceId ‖ phone_deviceId,
                      pt  = FK ‖ epoch ‖ deviceList)
```

An all-zero nonce is safe here and nowhere else: `wrap` is derived from a single-use rendezvous
value and is used for exactly one encryption in its lifetime. The code comment says so, and a test
asserts `wrap` is never handed to the message path.

### 3.4 What the relay learns, and the man in the middle it could otherwise be

During pairing the relay learns: a `roomId`, a `rendezvous` value, two device ids, two byte
strings it cannot decrypt, and two IP addresses. It does not learn `ss`, `wrap`, `FK`, or the
device name.

**But the QR authenticates only one direction.** The daemon's X25519 public key reaches the phone
over the user's own screen — a channel the relay cannot touch. The phone's public key travels back
*through the relay*, which could substitute its own and sit in the middle from that moment on.
This is the single sharpest attack on the whole design and it is the reason for the six digits: a
relay that substituted a key produces a different `ss`, therefore a different `sas`, therefore two
different numbers on the two screens, and the user's **Match** never happens.

Consequences, all deliberate:

- **The confirmation is mandatory.** There is no "skip", no "remember this device", no automatic
  match. A design that lets a hurried user tap past it is a design where the relay can read
  everything, and the whole product claim rests on this one dialog.
- Six digits is a 1-in-10⁶ blind guess for an active attacker who must also complete the exchange
  before the 120 s rendezvous expires. One attempt, then the rendezvous is burned. That is the
  standard short-authentication-string trade and it is stated here so nobody re-derives it later.
- The dialog names the device (`m`) so the user is confirming *something*, not just digits.

### 3.5 Device list, revocation, and rotation

The device list lives on every device and is the daemon's to edit:

```jsonc
{
  "roomId": "…",
  "epoch": 3,
  "devices": [
    { "deviceId": "…", "kind": "daemon", "name": "tower",  "x25519": "…", "ed25519": "…",
      "pairedAt": 1788…, "lastSeenAt": 1788… },
    { "deviceId": "…", "kind": "client", "name": "iPhone", "x25519": "…", "ed25519": "…",
      "pairedAt": 1788…, "lastSeenAt": 1788… }
  ]
}
```

The relay holds a **subset**: `deviceId`, `kind` and the Ed25519 public key, because it must
authenticate connections (§4.6). It never holds the name, the X25519 key or the pairing time.

**Revoking a device does three things, in this order and atomically from the user's point of
view:**

1. The device is removed from the list. Every daemon refuses its signature from that instant
   (§5.7), so it cannot act even if it still holds `FK`.
2. The relay is told, over the authenticated control channel, to close its connections and refuse
   its key. The relay is not trusted to do this — step 1 is what actually protects the floor —
   but it stops the noise.
3. **The epoch rotates.** A daemon mints `FK'`, increments the epoch, wraps `FK'` to each
   remaining device under `HKDF(X25519(this_daemon_id_priv, that_device_id_pub), …)`, and posts
   the wraps. No re-pairing, no QR, no user step. Every remaining device switches at the epoch
   boundary; envelopes at the old epoch are still accepted for 300 s so nothing in flight is lost.

The relay's queued ciphertext from before the rotation is still readable by the revoked device if
it can reach it, which is why the relay's queue TTL is short (§8.2) and why revocation also
instructs the relay to purge the room's queue. A user who has genuinely lost a phone is told, in
the revoke dialog, the true thing: *"Anything this device had already downloaded stays on it. New
activity is out of its reach from now on."*

Rotation also happens on a 30-day timer, so the code path that matters in an emergency is a path
that runs every month rather than one nobody has exercised.

### 3.6 Adding a second machine

Identical to §3.1 with the roles swapped: the new daemon shows nothing, the *existing* floor shows
the QR, and the new daemon reads it with `deckhq relay pair` — which prints a prompt for the
payload rather than requiring a camera. The new daemon receives `FK`, joins the room, and its
sessions appear on the floor within one snapshot. `machineId` is the one the ledger already minted
(§100), so history and live state agree about which machine a session was on from the first
second.

### 3.7 The account, and why it is only for the hosted relay

Signing in creates a relay account: an email address, a device code, and a subscription. The
daemon stores a bearer token in `~/.deckhq/relay.json` and nothing else about the person.

The account exists for billing and for abuse limits. It is **not** part of the cryptography: the
relay cannot derive `FK` from anything it holds about the account, and an account with no
subscription simply has no room. A self-hosted relay may be configured with no accounts at all
(§9.3).

The refusal that goes with it is in §11: **no account is ever required for the local product**,
and the local product does not know whether one exists.

## 4. Transport

### 4.1 One socket, and only when signed in

The daemon opens exactly one WebSocket, `wss://<relayHost>/v1/socket`, when `relay.json` exists,
parses, and carries a token. It is a client, not a server; there is no listening socket anywhere
in this design and no `--host` flag is added (C2).

Because C8 forbids a runtime dependency, the WebSocket client is written against `node:http` /
`node:https` and `node:crypto` — the RFC 6455 handshake plus a frame codec is roughly 300 lines
and is the largest single piece of WP-32. It supports what this protocol uses and nothing else:
binary frames, close, ping/pong, `permessage-deflate` **declined** (compression happens inside the
envelope, before encryption, where we control it).

`deckhq doctor` gains one row and keeps its old one honest:

```
  egress          none. no outbound sockets.                    ← signed out, unchanged
  egress          1 outbound socket: wss://relay.deckhq.dev     ← signed in, named
  relay           signed in · 2 machines, 1 phone · last sync 4s ago
```

Acceptance script item 30 (*"`deckhq doctor` reports zero outbound sockets after four hours of
use"*) stands unchanged for a signed-out daemon and is the regression test for C1.

### 4.2 The envelope

Binary frame, three parts: a canonical JSON header, the ciphertext, and an Ed25519 signature.

```
frame = uint16be(headerLen) ‖ header ‖ uint32be(ctLen) ‖ ciphertext ‖ sig(64)
```

| Header field | Type | What it is | Visible to relay |
|---|---|---|---|
| `v` | `1` | Protocol version | yes |
| `room` | 32 hex | Routing key | yes |
| `from` | 32 hex | Sender `deviceId` | yes |
| `to` | 32 hex or `"*"` | One device, or every other device in the room | yes |
| `epoch` | uint32 | Which `FK` this is under | yes |
| `seq` | uint64 as decimal string | Per `(from, epoch)`, monotonic. **Also the nonce** | yes |
| `cls` | `"d"` \| `"w"` \| `"c"` | Coarse class: data, wake-worthy, control | yes |
| `ts` | ms epoch | Sender's clock, advisory | yes |

`sig` is Ed25519 over `header ‖ ciphertext` by the sender's device key. The relay verifies it
before routing, so a party with a stolen `roomId` and no device key cannot inject a single byte.
Receivers verify it again, against their own device list, and that second check is what makes
revocation immediate (§3.5 step 1).

The ciphertext is `AES-256-GCM(key = K(from, epoch), nonce = epoch ‖ seq, aad = header, pt =
padded plaintext)`. Binding the whole header as AAD means the relay cannot alter `to`, `cls`,
`epoch` or `seq` without the tag failing.

Per-sender keys, so that each sender owns its own nonce space:

```
K(device, epoch) = HKDF(SHA-256, ikm = FK_epoch, salt = roomId,
                        info = "deckhq/msg/v1" ‖ epoch ‖ deviceId, 32)
```

Every device can derive every other device's message key, because every device holds `FK`. That is
not an oversight: within one floor all devices are the user's and the ciphertext authenticates
*the floor*, not the sender. Per-device authenticity comes from `sig`, which is the property
actions actually need, and it is the property revocation can withdraw.

### 4.3 Sequence numbers, nonce safety and replay

**Sending.** `seq` starts at 1 for each `(device, epoch)` and only increases. Before a daemon uses
any sequence number it reserves a block of 1,000 by writing `seqReserved = high + 1000` to
`relay.json` and waiting for the write to land. It then spends that block from memory. A crash
loses up to 999 unused numbers and can never reuse one. On start it resumes from `seqReserved`.
The phone does the same in IndexedDB. This is the whole defence against the GCM nonce-reuse
failure described in §2.4, it costs one small write per thousand envelopes, and it gets a test
that kills a daemon mid-block and asserts the next number is above the reservation.

**Receiving.** Per `(from, epoch)`: a high-water mark plus a 4,096-bit sliding window. A `seq`
below the window, or already set in it, is dropped and counted. WebSocket delivery is ordered, so
the window only exists to absorb reordering across a reconnect and the relay's queue drain.

**Replay across epochs is impossible** because the epoch is inside the nonce and the AAD, and
`K(device, epoch)` changes with it.

**Clocks.** `ts` is advisory and is never used for security. An envelope more than 300 s from the
receiver's clock is accepted, rendered with its own timestamp, and logged once — because the one
thing worse than a wrong timestamp on a phone is a phone that silently hides a session because a
laptop's clock is wrong.

### 4.4 What the relay can see, and what it cannot

**Can see — by design, and stated on the pricing page:**

| Visible | Detail |
|---|---|
| Room identity | `roomId`, and which account pays for it |
| Devices | `deviceId`, `kind` (daemon / client), Ed25519 public key, connect and disconnect times |
| Traffic shape | Envelope count, direction, size **bucket** (§4.5), `cls`, `seq`, `epoch`, `ts` |
| Network | Source IP and TLS metadata for every connection |
| Push | The subscription endpoint for each phone, which names the push service host (§7.1) |
| Billing | Email, subscription state, and whatever the payment provider holds (§12.3) |

**Cannot see:** session titles, conversation text, drafts, file paths, project names, project name
hashes, branch names, hostnames, machine names, `machineId`, runtime names, model names, token
counts, cost estimates, permission-request commands, decisions, ack state, or the contents of a
ledger day file. All of it is inside the ciphertext.

**Can infer, and we say so rather than pretend otherwise:** that you are working right now, roughly
how much, on how many machines, and — from a `cls: "w"` envelope — that something raised a hand.
§10 carries this as the residual risk it is. The mitigation for a user who cannot accept it is
§9: run the relay yourself.

### 4.5 Padding, compression and the two honest limits

Plaintext is framed `varint(realLen) ‖ payload ‖ zeros` and padded up to the next bucket:
**256 B, 1 KiB, 4 KiB, 16 KiB, 64 KiB, 256 KiB.** Anything larger is chunked into 256 KiB pieces
carried as consecutive envelopes, well under the Durable Objects 32 MiB received-message ceiling
(§14 R4) and well under any reasonable proxy's limit.

Compression (`node:zlib` deflate, and `DecompressionStream` on the phone) runs **before**
encryption, on payloads over 4 KiB. The usual objection to compressing before encrypting is the
CRIME/BREACH class, which needs an attacker who can inject chosen plaintext into the same
compression context as a secret. There is no such injection point here: a payload is one snapshot
or one day file, assembled locally, never mixing attacker-controlled and secret data in one
context. That is the reasoning; it is written down so a future reviewer can check the premise
rather than the conclusion, and the day a payload is ever assembled from a remote source, the
compression comes out.

Two limits stated plainly: **bucketing hides sizes, not activity**, and **nothing here hides
timing**. A relay operator watching a room sees the rhythm of a working day. Traffic padding to a
constant rate was considered and refused — it would burn a phone's battery and a laptop's radio
all day to obscure something the account's existence already implies.

### 4.6 Connection lifecycle

1. `GET /v1/socket` upgrade, with `roomId` and `deviceId` in the query and no secret anywhere in
   the URL.
2. The relay replies to the upgrade with a 32-byte challenge. The device signs
   `"deckhq/auth/v1" ‖ roomId ‖ deviceId ‖ challenge ‖ ts` with its Ed25519 key. The relay
   verifies against the registered key. Nothing is routed before that, and the challenge makes a
   captured handshake useless — the pattern Happy uses and the right one (§14 R6).
3. The relay drains the device's queue oldest-first, then goes live.
4. Ping every 30 s, both directions. Three missed pongs closes the socket.
5. Reconnect with full jitter: 1 s, 2 s, 4 s … capped at 60 s, plus up to 50% jitter, forever. A
   daemon that cannot reach the relay for a week is a daemon that retries once a minute and logs
   once an hour.
6. `4001 revoked`, `4002 no subscription`, `4003 room full` and `4004 version unsupported` are
   terminal: the client stops, records why, and shows it in Settings → Relay rather than
   reconnecting into a wall.

The Durable Objects note in §14 R3 — *"Code updates disconnect all WebSockets"* — means a relay
deploy drops every socket at once. The reconnect jitter above is what stops that from becoming a
thundering herd, and it is why the jitter is 50% rather than a token 10%.

## 5. What is relayed

### 5.1 The catalogue

| Stream | Direction | `cls` | Trigger | Cap |
|---|---|---|---|---|
| `snapshot/full` | daemon → `*` | `d` | On connect, on epoch change, after a diff gap | 256 KiB compressed |
| `snapshot/diff` | daemon → `*` | `d` | Each SSE `state` event, coalesced | 4/s, 32 KiB |
| `deck/order` | daemon → `*` | `d` | Inside every snapshot envelope | — |
| `permission/request` | daemon → `*` | `w` | `POST /api/permission` arrives (§97) | 32 pending, as `MAX_PENDING` already caps |
| `permission/decide` | phone → daemon | `c` | One tap | 1 per request |
| `action` | phone → daemon | `c` | One tap | 20/min/device |
| `send` | phone → daemon | `c` | Composer | 8 KiB text, 6/min/device |
| `send/progress` | daemon → device | `d` | `SendHub` events (WP-09) | 10/s |
| `notify` | daemon → `*` | `w` | The two budgeted interruptions (§7.3) | §7.3's budget |
| `history/day` | daemon → `*` | `d` | A day closes, or a device asks | 1 object per (`machineId`, day) |
| `control/*` | any | `c` | Device list, epoch wrap, revocation, presence | — |

### 5.2 The snapshot diff stream: SSE → envelopes

`GET /api/events` already pushes the whole `registry.snapshot()` on every change (`02` §5,
`src/http/routes/state.mjs`). The relay client subscribes to the same in-process
`registry.on(…)` callback the SSE route uses — not to its own HTTP request, which would be a
loopback socket serving the machine's own daemon for no reason.

Three transformations happen before an envelope leaves:

1. **Coalesce.** At most one envelope per 250 ms, and never more than 4/s. A cold scan moves 90
   sessions at once and a phone does not need 90 frames of it.
2. **Diff.** The daemon keeps the last snapshot it sent per epoch and emits changed agents only,
   as `{ agents: { added: [...], changed: [{id, …fields}], removed: [ids] }, counts, projects? }`.
   A diff whose `seq` the receiver has not seen contiguously is answered with a `control/resync`
   and the daemon sends a full snapshot. There is no merge cleverness: a gap means resync.
3. **Trim.** `lastText` is already `≤ 400` chars (`02` §3). Nothing else is trimmed unless the
   256 KiB cap is hit, and then `lastText` goes first, then `currentTool`, and the envelope says
   `trimmed: ['lastText']` so the phone renders *"(text not sent — snapshot too large)"* rather
   than an empty quote that looks like the agent said nothing.

### 5.3 The deck

§103 settles what the phone shows: **the deck, not the floor.** A five-inch screen renders a queue
well and an isometric office badly, and the deck is already the accessible, semantic, queue-ordered
equivalent of the floor.

The ordering rule now exists twice — `groupRows()` in `src/cli/deck.mjs` and `queueGroups()` in
`public/deck.js` — and §103.1 explains why, and rejects sending the order in the snapshot payload.
**That rejection does not extend to the relay, and this is a deliberate departure from §103.1.**
Its three reasons were all about the local client: a field the daemon may not have sent yet, a
snapshot field for something the client can compute instantly, and the CLI needing its own copy
anyway. On the wire, none holds: the phone has no access to `src/`, cannot import either
implementation, and a third copy in a separate PWA codebase is exactly the drift §103.1 exists to
prevent. So the snapshot envelope carries `deckOrder: [agentId, …]`, computed by `groupRows()`,
and WP-32 ships the test that already exists in spirit: `groupRows()`, `queueGroups()` and
`deckOrder` over one fixture, three id sequences, asserted equal.

The phone's floor view is a **second** tab and it reuses `Scene` as a third render target, exactly
as the mini-floor does (§113): `frame()`, `stepIfPaused(dt)`, `colorForAgent`, `iconForAgent`, the
office-plus-corridor shot, and `lodForZoom(characterScale / U)` because LOD keys off the scale a
*body* is drawn at (§113.3). The one cost the mini-floor does not pay is the bake: a phone with no
main floor behind it must bake its own backdrop, ~190 ms, once per open. That is acceptable for a
tab the user opens deliberately and it is why the deck is the home screen and this is not.

### 5.4 Permission requests, across the wire

The panel's behaviour (§97) is the contract; the wire adds three things and removes none.

- The request envelope carries what the card carries: `{ id, tool, summary, suggestions,
  requiresUserInteraction, since }` and, new, **`deadline`** — the absolute ms epoch at which the
  daemon will release the hold. The daemon's hold is already `600_000 − 15_000` (§97.2 decision
  2); the relay path subtracts a further 10 s round-trip budget, so `deadline = since + 575_000`.
  The phone renders a countdown, and at zero it replaces the buttons with *"Expired. No decision
  was made — the terminal has it."* That sentence is the truth §97 already enforces: the hold
  expires into no decision at all.
- A decision is a `permission/decide` envelope. It reaches the daemon's existing
  `POST /api/permission/decide` funnel — the same function, not a parallel one — after two checks:
  the signature verifies against a device in the current list, and the request is still pending.
  A decision for an expired or already-answered request is refused with a reason the phone shows.
- **Two phones, one request.** First decision wins; the second gets `already_decided` and the card
  on that phone shows who decided and when. `MAX_PENDING = 32` is unchanged; a floor with more
  than 32 pending permissions has a bigger problem than a phone.

The five refusals in §97.2 are inherited verbatim and get wire-level tests of their own: no
auto-allow on any heuristic, no answer on a timer, never `interrupt: true`, never a `destination`
other than `"session"`, and never a touch of `ackState` / `reviewSince` / `needsInputSince`.

### 5.5 Actions and sends: the phone presses a button, it does not set a state

An `action` envelope is `{ actionId, agentId, action }` where `action` is one of the six in
`02` §5.1. On arrival the daemon:

1. verifies `sig` against a device **currently** in the list;
2. checks `actionId` (128 random bits, minted by the phone) against a 10-minute LRU of applied
   ids, and if it is a repeat, re-acknowledges without re-applying;
3. checks that the agent is one **this machine owns** (§6.1) — an action for another machine's
   session is forwarded, not applied;
4. calls `act()`. The same function the floor calls. Same legality table, same ledger record, same
   error on an illegal transition.

There is no second path into ack state, and that is asserted the way `public/panel.js`'s
invariant already is (§97.2): a static test greps `src/relay/` for `setAck`, `reviewSince`,
`needsInputSince` and `store.mjs` and fails on any of them. The relay client can reach `act()` and
nothing else.

`send` reaches `SendHub` unchanged and its progress streams back over `send/progress` (WP-09), so
a reply typed on a phone streams to the phone and to every open floor at once.

**`POST /api/open` is never relayed.** Spawning a terminal on a machine you are not sitting at is
not a feature, it is a remote-execution primitive with a friendly name. Refused in §11.

### 5.6 History

When a local day closes, each daemon encrypts that day's ledger file whole — the same bytes
`deckhq ledger export` writes — and posts it as `history/day` keyed `(machineId, dayKey)`. The
relay stores the ciphertext object, capped and TTL'd (§8.2). A phone paired later asks for the
window it lacks and rebuilds the same statistics from the same records, because `computeStats`
runs over parsed records and the phone has the records.

Four properties carry over from §100 unchanged and are worth naming, because they are why the
ledger was the right substrate for this: a day file is **self-contained** (the per-day
`first_seen` carry-over), it holds **no path and no project name** (`projectKey` is a hash), it
already carries **`machineId`** on every record, and `--signed` gives an Ed25519 signature with the
public half beside it. The relay is handed a file that was designed for a hostile reader before
the relay existed.

Retention on the relay is `min(settings.ledgerRetentionDays, 90)`, defaulting to 90 — the number
`03` §3.1 sells. A user who sets local retention to 7 days gets 7 on the relay; the relay never
holds history the machine has already forgotten.

### 5.7 The invariant, across the wire

`docs/01-PRODUCT.md` §2 is one sentence and the relay adds four new ways to break it. Each has a
named enforcement point and each gets an `INVARIANT:` test in WP-32, in the style of the existing
ones.

| The way it could break | Why it cannot |
|---|---|
| A phone renders a session and that counts as reading it | The phone has no write path. Rendering, scrolling, opening a card and expanding a diff send nothing. `INVARIANT: the phone client sends no envelope on any read` |
| A push is delivered, or tapped, and the queue clears | Delivery is the push service's event, not the user's. The notification tap opens the deck and nothing more. `INVARIANT: notification delivery and activation produce no action envelope` |
| A snapshot arriving at a daemon overwrites its state | **Daemons never accept state from the wire.** A `snapshot/*` envelope received by a daemon is dropped and counted. Only `action`, `send`, `permission/decide` and `control/*` are processed inbound, and only for sessions this machine owns. `INVARIANT: an inbound snapshot changes nothing on a daemon` |
| A replayed or duplicated action applies twice | §4.3's window plus §5.5's `actionId` LRU. `INVARIANT: a replayed action envelope acknowledges and does not re-apply` |

And the fifth, which is a user-experience rule rather than a state rule but comes from the same
place: **an action that has not reached its daemon must never look applied.** The phone marks the
row *sending…* and turns it *done* only when a snapshot shows the state actually changed. If the
owning daemon is offline the row says *"`tower` is offline — this is queued"* and stays queued.
Optimistic UI is the correct default in most products and is wrong in this one: the whole promise
is that what you see is what is true.

## 6. Multi-machine: one floor from N daemons

### 6.1 Ownership, not merge

Every daemon is the sole authority for the sessions on its own machine. Nothing is merged about a
session: the agent record for `claude-code:abc…` comes from exactly one daemon, carries its
`machineId`, and no other daemon may write it. The phone's floor is a **union**, and a union has
no conflicts.

This is the choice that makes the multi-machine story small. Last-writer-wins over shared records
would have needed vector clocks, tie-breaks, and a story for two machines disagreeing about
whether you had acknowledged something. Ownership needs none of it and matches the truth: the
session is on one machine, and the acknowledgement is a fact about that machine's `state.json`.

`agentId` is already `runtime:session-uuid` and globally unique (`02` §3), so a union needs no
renaming. Every agent gains one field on the wire, `machineId`, and the phone gains one chip.

### 6.2 Rooms, and the suffix rule

`projectKey` is SHA-256 of the normalised directory (§100 decision 5), so:

- The same absolute path on two machines produces the same key. **One room, desks from both
  machines**, which is what a user who syncs a working tree between a laptop and a desktop
  expects.
- `~/code/api` on a Mac and `C:\code\api` on Windows produce different keys, so **two rooms**, and
  the two rooms have the same display name.

The name collision is resolved with a machine suffix, and only when it collides: a room plate
reads `orbital-api` when it is unambiguous and `orbital-api · tower` when a second room shares its
name. The rule is the smallest one that never lies and never adds noise to the common case.
Merging two paths the user considers the same project is a manual link in Settings → Relay, is
recorded per floor, and is out of scope for WP-32 — named here so the absence is a decision rather
than an oversight.

### 6.3 Conflicts, such as they are

| Situation | Rule |
|---|---|
| Two daemons claim one `agentId` | Impossible by construction; if seen, the newer `lastActivityAt` wins and both are logged loudly, because it means a `state.json` was copied between machines |
| Two machines share a `machineId` | Same cause, same remedy: the phone shows a warning naming both, and `deckhq relay doctor` offers to re-mint |
| A daemon is offline | Its agents stay on the floor, dimmed, with *"`tower` last seen 2h ago"*. They are **not** removed: an absent machine is not an absent session, and removing them would silently shrink the queue |
| Two phones act at once | Both actions reach the owning daemon and `act()` orders them. The second may be a no-op; the legality table already says so |
| Clock skew between machines | Durations are computed from each machine's own timestamps and rendered with their own machine's label. No cross-machine arithmetic anywhere, so skew cannot produce a negative wait |

### 6.4 History merges, files do not

`history/day` objects are stored and rendered per `(machineId, day)` and are never concatenated
into one file. Statistics are computed by walking all of them, which is what `computeStats`
already does over a directory. Two machines' medians combine into one median over the union of
episodes; "longest wait ever" is a max over the union; "the room that never slept" names the
machine when the room is machine-specific.

## 7. Push

### 7.1 The shape of the problem

Web Push has two independent encryption layers and the design needs both, for different attackers.

- **RFC 8291** already encrypts the payload from the *application server* to the browser with
  aes128gcm over an ECDH P-256 agreement, so the push service cannot read it (§14 R9). That
  handles Google, Apple and Mozilla.
- **But the relay is the application server.** It holds the VAPID key pair (RFC 8292), it composes
  the request, and it therefore sits *inside* RFC 8291's trust boundary. If the daemon handed the
  relay a notification body, the relay would read every notification. That would make "the relay
  cannot read anything" false in exactly the place users would most notice.

So the daemon must never hand the relay a plaintext body.

### 7.2 The two payload modes

**Default: an opaque wake token.** The daemon sends a `cls: "w"` envelope. The relay pushes a body
containing 16 random bytes and nothing else — no agent name, no project, no count, no
identifier that means anything outside the room. The service worker wakes, opens a short-lived
authenticated socket, drains the queue, decrypts under `FK`, and shows the real notification.

Chrome and Edge require `userVisibleOnly: true` (§14 R2), so the worker **must** show something.
If it cannot reach the relay within 4 s it shows the fallback — *"DeckHQ — something needs you"* —
which leaks nothing beyond the fact that the app pushed, which the push service already knows.
That fallback is a feature: it is what makes the strict mode honest rather than a silent failure.

**Optional: a double-encrypted payload.** For users who want the notification text to survive a
phone with no connectivity at the moment of delivery, the daemon encrypts the notification body
under `FK` — `AES-256-GCM`, same envelope discipline, `≤ 512` bytes of ciphertext — and hands the
relay an opaque blob to place in the push payload. The relay places bytes it cannot read; the push
service carries them under RFC 8291's own encryption; the service worker decrypts twice.

Budget arithmetic, so nobody rediscovers it at 2am: a push service must support at least **4096
bytes** of encrypted payload (§14 R1). RFC 8188/8291 framing costs a 16-byte salt, a 4-byte record
size, a 1-byte key-id length, a 65-byte key id and a 16-byte GCM tag, plus one padding delimiter —
**103 bytes**, leaving 3,993. Our 512-byte ceiling sits far inside it with room for base64 if a
provider needs it. Bodies longer than the ceiling are truncated to the coalesced form
(*"3 sessions raised a hand"*), never to a half sentence.

The default is the wake token. The mode is one switch in the phone's settings, worded as the trade
it is: *"Notification text on the lock screen even when offline. The relay still cannot read it;
your push provider still cannot read it; it does mean an encrypted copy of the text passes through
both."*

### 7.3 The interruption budget, enforced on the phone

`04-ENGAGEMENT-AND-GAMIFICATION.md` §6 budgets exactly two interruptions and §101 implemented them.
The relay does not get to spend more.

| Event | Notifies | Why |
|---|---|---|
| `needs_input` entered | **yes**, once, on entry | A raised hand |
| A session dies unexpectedly while working | **yes**, once | §101's `closedCleanly` rule, computed on the daemon where the hook evidence lives |
| `for_review` entered | no — badge only | §101 §4, asserted by a test that fails if a state is added |
| `stalled` entered | no — badge only | Same |
| Anything else | no | There is no third interruption and §11 refuses to add one |

Three rules on top, all on the phone because the phone is the only party that knows what this user
has already been shown:

1. **Coalescing is the client's 10 s window, unchanged.** Three hands inside it become one
   notification reading *"3 sessions raised a hand"*, exactly as §101 §7 asserts.
2. **A first sight is not an event.** A phone that has been asleep for two days and wakes to
   eleven raised hands shows the badge and **one** summary, never eleven notifications. §101
   already refuses to replay a backlog on daemon restart; the same rule, on the same grounds.
3. **The copy carries no second-person fault.** *"Ada raised a hand in orbital-api"*; never *"you
   left"*, never *"you forgot"*. WP-33 ports §101's grep test — `you`, `your`, `forgot`, `left`,
   `neglect`, `ignored`, `abandon` — over every string the phone's composer can produce.

The badge is `navigator.setAppBadge(needsYou)`, which iOS Home Screen web apps support from 16.4
(§14 R5), and it is the surface that carries everything the budget refuses to interrupt for.

The relay enforces a hard rate limit underneath all of it — **1 push per 10 s per device, 30 per
hour** — because a rate limit that lives only in the client is a rate limit a bug can remove.

### 7.4 The iOS reality, stated once

On iOS and iPadOS, Web Push works **only for a web app added to the Home Screen**, from 16.4, with
a manifest, and permission must be requested from a direct user gesture (§14 R5, R2). So WP-33's
onboarding is: install to the Home Screen → open from the Home Screen → tap **Turn on
notifications**. There is no way around it and the PWA must say so plainly rather than showing a
permission prompt that silently cannot appear. `public/manifest.webmanifest` and `public/sw.js`
already exist (§101 §6) and the phone's worker is a sibling, not a fork — with the same two
refusals: it caches nothing and it intercepts nothing.

`UNVERIFIED` — that Safari on iOS delivers a push whose payload our worker can decrypt with a
non-extractable IndexedDB key while the app is not foregrounded. It follows from the standards
being the same ones (§14 R5) but it has not been run, and §101's deviation 4 is the standing
lesson: the PWA's own installability was written down as verified when only its manifest had been
checked.

### 7.5 Where the phone's keys live

`FK` and the device private keys are stored in IndexedDB as **non-extractable** `CryptoKey`
objects, so page script can use them and cannot read them. Consequences accepted: clearing site
data un-pairs the phone (the UI says so before it happens), and a second browser profile is a
second device. A phone with no OS lock screen is a phone that has handed over the floor, and §10
says so rather than pretending IndexedDB is a secure element.

## 8. Offline, degraded, rate limits, abuse

### 8.1 Degradation, in the order it will actually be met

| What is down | The floor | The phone | What is said |
|---|---|---|---|
| The relay | Fully working. Local floor, local panel, local actions, local everything | Last snapshot, read-only, dimmed | Floor: one chip, *"Relay unreachable — retrying"*. Phone: a banner with the age of what it is showing |
| One daemon | Its own machine is fine | That machine's agents dim; their actions queue | *"`tower` last seen 2h ago"* |
| The phone | Nothing changes | — | Nothing. A phone is not a dependency |
| The push service | — | Badge and in-app only | Nothing. A missing push is not an error worth interrupting for |
| The subscription lapsed | Fully working | Read-only for 7 days, then paired but empty | Floor: *"Relay off — the floor is unaffected"*. C9: no local feature is withdrawn |

The first row is the one that matters and it is worth stating as a rule: **the relay is never in a
critical path on the local machine.** It subscribes to the registry and writes to a socket. If it
throws, the throw is caught, counted, and the floor does not notice — the same discipline the
ledger already has (§100), and for the same reason.

### 8.2 Limits

| Limit | Value | Why |
|---|---|---|
| Devices per room | 16 (8 daemons, 8 clients) | Above this it is a team, which is a different product and a different price |
| Envelopes | 20/s burst, 5/s sustained per device | A coalesced diff stream is under 4/s |
| Bytes | 200 MiB/device/day | Roughly a hundred full snapshots plus a day of diffs |
| Queue per offline device | 2,000 envelopes or 16 MiB, whichever first, **TTL 7 days** | Enough for a weekend; short enough that a revoked device's window is small (§3.5) |
| Queue overflow | Drop oldest `snapshot/diff` first, then `send/progress`; **never** drop `permission/*` or `action`; on any drop, set a resync flag | A dropped diff costs a resync; a dropped decision costs a session |
| History objects | 90 days × 8 machines, 1 MiB/day/machine | §100 measures 46 KB/day on the reference machine, so this is 20× headroom |
| Push | 1/10 s/device, 30/hour | §7.3 |

Exceeding a limit closes the socket with a named code and a `Retry-After`; it never silently
discards.

### 8.3 Abuse

- **No unauthenticated write, ever.** §4.6's challenge-response is required before a byte is
  routed, and every envelope is signed. Knowing a `roomId` grants nothing.
- **A `roomId` is not a bearer token.** It is a routing key. This is deliberate: routing keys leak.
- **Signature verification at the relay** stops a compromised account from injecting into a room it
  can see, and stops the relay's own operators from doing it accidentally.
- **Account abuse** — a subscription buying bandwidth for something else — is bounded by §8.2 and
  by the room's device cap. The relay does not proxy arbitrary hosts, has no upload endpoint
  outside the queue, and serves no content to anyone but a signed device.
- **Enumeration.** `roomId` and `deviceId` are 128 random bits. Failed authentications are rate
  limited per IP and per room, and the relay's replies do not distinguish "no such room" from "bad
  signature".
- **Denial of service against a floor.** A relay under attack degrades to §8.1 row 1, which is a
  fully working local product. This is the deepest benefit of local-first: our worst outage is
  someone else's feature request.

## 9. Self-hosting

### 9.1 What ships

`deckhq-relay`: a single Node program, **zero runtime dependencies**, Node ≥ 18, that speaks the
protocol in §3–§7 and holds its state in SQLite (`node:sqlite`) or a directory of files. Plus a
Docker image, a 30-line `docker-compose.yml`, and a page of documentation.

```
docker run -p 8443:8443 -v deckhq-relay:/data ghcr.io/dkpanseriya/deckhq-relay
deckhq relay login --url https://relay.example.com
```

There is no default relay URL compiled into the daemon. `relay.json` names one, or
`DECKHQ_RELAY_URL` does. A daemon with neither has no relay code loaded at all (C1).

### 9.2 The licence split

| Half | Licence | Where |
|---|---|---|
| Client (`src/relay/`, the PWA, the protocol tests, the vectors) | **MIT**, in the main repository | Auditable by anyone, which is the point of publishing a protocol |
| Server | **Source-available**, separate repository | Self-hosting for your own use is free and explicitly permitted; offering it as a service to others is not |

Recommendation: **FSL-1.1-Apache-2.0** — read the source, run it for yourself, no competing hosted
service, and it converts to Apache 2.0 after two years. BUSL-1.1 with a four-year conversion is the
conservative alternative. This is an owner decision (§13), and the design does not depend on which
is chosen. What the design does depend on is that **the client half is MIT**, because a threat
model nobody can check against running code is a press release.

### 9.3 What a self-hoster gets, and what they must do

Gets: the whole protocol, their own VAPID key pair, their own retention, no account system if they
do not want one (`RELAY_OPEN_ROOMS=1` accepts any room whose devices authenticate), and a
`--print-metrics` that shows exactly the metadata §4.4 says a relay can see, so an operator can
verify the claim on their own box.

Must do: terminate TLS, generate VAPID keys (`deckhq-relay keygen`), and keep the clock roughly
right. Push through a self-hosted relay works exactly as it does through ours, because VAPID is a
key pair, not a business relationship (§14 R9, R2).

The commercial logic is unchanged from `03` §3.2 and worth restating: the people who self-host were
never going to pay, and their existence is what makes the promise checkable for the people who do.

## 10. Threat model

`FK` = the floor key. "Content" = titles, text, paths, project names, hostnames, models, tokens.

| Attacker | Can do | Cannot do | Mitigation | Residual |
|---|---|---|---|---|
| **Relay operator** (including us, compelled or compromised) | Read all metadata in §4.4; drop, delay, reorder, count; correlate IPs; observe working rhythm; attempt a pairing MITM | Read content; forge an envelope; replay one; apply an action; recover `FK` | AEAD with the header as AAD; Ed25519 per envelope, verified again by the receiver against the local device list; SAS confirmation at pairing (§3.4); short queue TTL | **Traffic analysis is unmitigated and stated on the pricing page.** A user who cannot accept it self-hosts (§9) |
| **Network attacker** (café Wi-Fi, hostile ISP, TLS-terminating middlebox) | Observe TLS metadata; block; delay | Read content even with a trusted-root MITM, because the payload is encrypted under `FK` beneath TLS | Two independent layers; certificate pinning to the configured host after first success | Blocking is a denial of service, which degrades to §8.1 row 1 |
| **Lost or stolen phone** | Read everything the phone holds and had cached; act as that device until revoked | Act after revocation; read anything sent after the epoch rotation | Non-extractable keys (§7.5); revocation is instant at every daemon (§3.5 step 1); rotation is automatic, not a thing to remember; the relay's queue is purged | An unlocked phone is a full compromise until the user notices. There is no remote wipe and §11 refuses one |
| **Malicious or compromised daemon** (a machine already owned) | Everything: it has `FK`, the transcripts, and `act()` | — | None, and none is possible | **Out of scope, honestly.** A machine running the user's agents with the user's credentials is already the crown jewels. The relay does not widen this and must not be sold as narrowing it |
| **Malicious phone** (paired, then turned) | Read the floor; act on any session; send text to any session; decide permissions | Escape the action set: no `open`, no shell, no file read, no arbitrary API | Every inbound envelope goes through `act()` / `SendHub` / `decide()` and nothing else (§5.5); `/api/open` is not relayed; sends are capped and rate limited; every action lands in the ledger with its device | A paired device is a trusted device. The remedy is revocation, and the device list is on the floor where the user will see a device they do not recognise |
| **Push service** (Google / Apple / Mozilla) | See that a push happened, to which endpoint, how large, how often | Read the notification text | RFC 8291 to the browser, plus `FK` beneath it (§7.2) | Timing and volume, same as the relay |
| **Someone with only a `roomId`** | Nothing | Connect, read, write | §4.6 challenge-response | — |

**The three properties this design does not provide, named so nobody assumes them:**

1. **No forward secrecy.** Device identity keys are long-lived. An attacker who records the
   relay's traffic and later compromises a device key can decrypt the wrapped `FK` from that
   epoch and thus that epoch's traffic. Mitigations are partial and real: epochs rotate on
   revocation and every 30 days, and the relay's queue keeps 7 days. A double-ratchet would fix it
   properly and is refused in §11 with its reason.
2. **No metadata privacy.** §4.4, §4.5.
3. **No protection from your own machine.** Row 4.

## 11. What is deliberately not built

Each of these is a refusal with a reason, and each is the kind of thing a reasonable person will
propose in month five.

1. **No server-side storage of plaintext. Ever.** Not for search, not for a web dashboard, not for
   "just the titles so we can render a nicer notification". The moment one plaintext field lives on
   the relay, every sentence in §1.2 becomes a footnote.
2. **No account required for the local product**, and no check for whether one exists (C1). The
   free daemon does not know the relay exists.
3. **No telemetry.** Not on the daemon, not in the PWA, not on the relay beyond the operational
   metadata in §4.4 that routing cannot avoid. No analytics SDK, no error reporter, no session
   replay. `03` §6: the zero-egress promise has no asterisk.
4. **No `/api/open` over the wire.** §5.5.
5. **No server-side notification composition.** The relay never writes a word a user reads. §7.2.
6. **No optimistic UI on the phone.** §5.7.
7. **No remote wipe, no "log out all devices" that pretends to reach into a phone.** Revocation is
   honest about what it can and cannot do (§3.5).
8. **No key escrow, no account recovery of `FK`.** A user who loses every device loses the room's
   history and re-pairs from a machine. Anything else is a back door with a support ticket
   attached.
9. **No double ratchet in v1.** It is the correct answer to §10's first residual and it is weeks of
   work with a large correctness surface, for an attacker who must first compromise a device that
   already holds the transcripts in plaintext on disk. Revisit if the threat model changes; do not
   build it because it sounds better.
10. **No relay-side cron, no "daily card from the cloud", no server-rendered Wrapped.** Those are
    computed on a device from records the relay cannot read, and they stay there.
11. **No gate on any local feature, at any tier** (C9). The floor, the deck, the panel, the six
    actions, the invariant and every adapter are the same signed in and signed out.

## 13. Open questions for the owner

Named because they are not the Architect's to decide, and because WP-32 can be built to day 9
without any of them.

1. **Relay hosting provider.** Cloudflare Workers + Durable Objects is the assumed host and the
   fit is good: one Durable Object per room is the natural shape, the Hibernation API means an idle
   room costs no duration billing, and the 32 MiB received-message ceiling is far above our 256 KiB
   frame (§14 R3, R4). Against it: *"Code updates disconnect all WebSockets"*, an outbound
   WebSocket keeps an object alive only up to 15 minutes per connection, and the reference relay
   must run on plain Node anyway for §9 — so either the server is written twice or it is written
   once for Node and deployed on a VM. **Recommendation: write it once, for Node, and host it on a
   small VM behind Cloudflare.** The Durable Objects version becomes an option if room counts
   justify it. Owner's call.
2. **Domain.** `relay.deckhq.dev` is assumed throughout. It is not registered. The daemon has no
   default host compiled in either way, so the answer changes one line of documentation.
3. **Pricing page copy.** §4.4's two lists are the honest version and they are unusually blunt for
   a pricing page. Someone has to decide whether *"the relay can see when you are working and how
   much"* appears above or below the fold. The Architect's position: above. It is the sentence that
   makes the rest believable, and every competitor's page is silent about it.
4. **The server licence.** FSL-1.1-Apache-2.0 (recommended) or BUSL-1.1 (§9.2).
5. **VAPID key custody**, and what happens on rotation: keys live with the relay operator, so ours
   are one more secret to hold and a self-hoster generates their own. Rotation invalidates every
   subscription and every phone must re-subscribe. Acceptable, needs an owner-approved plan.
6. **Default history retention on the relay.** 90 days is what `03` §3.1 sells; the ledger's local
   default is also 90 (§100). Confirm they should stay coupled.
7. **`machineId` on the wire.** §100 decision 6 already flagged the identifier for the owner's
   confirmation and noted that nothing in the repository sends it anywhere. The relay changes that:
   it is sent, encrypted, to the user's own devices, and never in clear. Confirm.
8. **Whether `osNotify` should default on once the phone exists** — §101 §5 left this open pending
   WP-19, and a phone that buzzes makes a desktop toast either redundant or a duplicate.
